# 同期は clone から始め、状態が疑わしければアップロードを止める

これまで、同期先を設定した直後の同期はいきなり三方向マージを始めていた。ベースラインが無い状態では、ローカルの全ファイルが「リモートに無い新規ファイル」となり、そのまま共有Vaultへ上がる。新しく参加した人が自分の個人ノートをチーム全員に配る経路が、ここにあった。

逆の事故も起きた。Vault の中身を消してからプラグインを有効化すると、ベースラインだけが残っているため、全ファイルがローカルで削除されたと解釈される。削除の安全上限（ADR-0001）が働いて実行はされないが、保留された削除は毎回同じ判断に戻る。ダウンロードもアップロードも進まないまま、Vault は空のままになる。安全ではあるが、そこから抜け出す手段が無かった。

どちらも根は同じである。**ベースラインが現実と合っていない状態で、同期が黙って走る。**

そこで二つ決める。ひとつ、ベースラインが無いときに押せるのは clone だけにする。clone はリモートをローカルに再現する非破壊の操作で、ローカルにしか無いファイルは消さず、同名で中身が違うファイルはローカル版を `.conflict-<UTC>` に退避してからリモート版を置く。初回接続も、2 台目の端末も、壊れた状態からの復旧も、すべてこの一本の経路を通る。

ふたつ、状態が疑わしいと分かる条件を三つ決め、当てはまる間はアップロードを止める。(1) 削除が安全上限を超えた、(2) ローカルが空でベースラインが空でない、(3) ベースラインが無いのに両側に中身がある。止めるのはアップロードだけで、ダウンロードは続ける。危ないのは送信側だけであり、受信を止めると、復旧作業をしている人が他の全員の更新から切り離される。

## Consequences

- 止まった状態から抜ける道を、必ず二つ用意する。clone でやり直すか、保留された削除を承認するかである。承認はファイル単位で選べ、既定では何も選ばれていない。これが唯一、チームのデータを実際に消す操作になる。
- clone が退避した `.conflict-<UTC>` のファイルは、リモートに存在しないためローカル固有として扱われる。放置すればチーム全員に競合コピーが配られるので、分類を終えるまでアップロードは止まったままになる。
- 「リモートが空でローカルに中身がある」は検知条件に含めない。チームの最初の一人が共有Vaultを作る正常な手順と区別できないためである。その経路も clone を通るので、条件 (3) で足りる。
- 既存の利用者には clone を要求しない。ベースラインの形式は変わっておらず、疑わしい条件に当てはまらない限り、これまでどおり同期を続けられる。
