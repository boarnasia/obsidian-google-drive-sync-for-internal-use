# 同期の仕組み

このプラグインが、いつ、何を比べて、どう決めているかの説明です。用語は [CONTEXT.md](../CONTEXT.md) に従います。

## いつ同期が走るか

| きっかけ | 動き |
|---|---|
| ローカルでファイルを編集・作成・削除した | 編集が 3 秒落ち着いてから同期する |
| 一定間隔（既定 1 分） | まずローカルがベースラインから変わっていないかを確かめ、変わっていれば同期する。変わっていなければ、変更プローブで Drive 側の同期ルートの中に変更があったかだけを確かめる。どちらも無ければ何もしない |
| サイドバーの「今すぐ同期」 | その場で同期する |

同期は同時に一つしか走りません。同期中に編集があれば、終わった直後にもう一度走ります。

ローカルの確認は、変更イベントを取りこぼした編集（Obsidian を閉じている間の編集、失敗した同期など）を拾うためのものです。更新日時とサイズが前回と同じファイルは読み直さないので、Drive への問い合わせも発生しません。ただし直近の同期が要確認状態で止まっているときは、同期し直しても止まるだけなので、ローカルの差分では同期しません。

自動同期が失敗しても通知は出ません。代わりにサイドバーに失敗の理由を表示します。

同期の本体は、同期ルート以下のフォルダを全部たどってリモートの一覧を作る処理です。フォルダの数だけ Drive に問い合わせるので、数十秒かかることがあります。変更プローブは、この重い処理を必要なときだけ走らせるためのものです（[ADR-0002](adr/0002-changes-api-as-trigger.md)）。

Drive の変更ログはドライブ全体のものです。同じ共有ドライブの別のフォルダで作業があっても、同期ルートの中の変更でなければ同期しません。中か外かは、直前の同期でたどったフォルダとファイルの ID で判断します。Obsidian を起動した直後はこの ID がまだ無いので、最初の確認では変更の中身を見ずに同期します。

保存した変更ログの位置（ページトークン）を Drive が受け付けなくなった場合も、同期して位置を取り直します。

## 何を比べているか

ファイルの更新日時ではなく、**ベースライン**との差で判断します。ベースラインは、前回の同期が成立した時点の各ファイルの記録です。

- ローカル側: 内容のハッシュ（SHA-256）
- リモート側: Drive が返す `md5Checksum`

同期のたびに、現在のローカル・現在のリモート・ベースラインの三つを突き合わせます（三方向マージ）。

| ローカル | リモート | 動作 |
|---|---|---|
| 変化なし | 変化なし | 何もしない |
| 変更 | 変化なし | アップロード |
| 変化なし | 変更 | ダウンロード |
| 変更 | 変更 | **競合**として解決する（次節） |
| 削除 | 変化なし | リモートを Drive のゴミ箱へ |
| 変化なし | 削除 | ローカルを OS のゴミ箱へ |
| 削除 | 変更 | リモート版をダウンロードして復元 |
| 変更 | 削除 | ローカル版をアップロードし直す |

削除と変更がぶつかったときは、残っている方の内容を守ります。

## 競合の解決

ベースライン以降に、ローカルとリモートの両方が変わった場合です。

1. リモートの内容を取得し、ローカルと比べる。**内容が同じなら競合ではない**。そのままベースラインに記録する。
2. 内容が違えば、更新日時の新しい方を正とする。
3. 正とされなかった方は、ローカルに **競合コピー** `<名前>.conflict-<UTC日時>.md` として残す。

例:

| 時刻 | 出来事 |
|---|---|
| 10:00 | 同期。ベースラインに A の v1 を記録 |
| 10:09 | 他のメンバーが A を v2 に更新 |
| 10:10 | 自分が A を v3 に更新して同期 |

リモートは v1 から v2 に、ローカルは v1 から v3 に変わっているので競合です。ローカル（10:10）の方が新しいので v3 をアップロードし、v2 は `A.conflict-….md` としてローカルに残ります。

リモートの更新日時は Drive にアップロードされた時刻で、実際に編集した時刻より遅れることがあります。そのため、リモートがローカルより**厳密に**新しいときだけリモートを正とします。PC の時計がずれていて勝ち負けが逆になっても、負けた側は競合コピーとして残るので、内容は失われません。

競合コピーはリモートに無いファイルなので、ローカル固有ファイルとしてサイドバーに並びます。中身を確かめてから「共有」か「削除」を選んでください。

## 削除とゴミ箱

- リモートの削除は Drive のゴミ箱へ、ローカルの削除は OS のゴミ箱へ送ります。OS のゴミ箱が使えないときは Vault 内の `.trash` に移します。どちらも完全には消しません。
- 一度の同期で消すファイルが `max(10, 追跡中のファイル数の 20%)` を超えたら、削除を実行せずに保留します。保留された削除は、サイドバーでファイルごとに承認するまで実行されません。
- ファイルの名前変更やフォルダの移動は、「元のパスから消えて、同じ内容が別のパスに現れた」として扱い、削除には数えません。

ベースラインと現実が食い違っている疑いがあるときは、アップロードだけを止めます（要確認状態）。条件と抜け方は [同期モードと同期管理サイドバー](design/sync-modes.md) にあります。

## 既知の問題

### 同期の途中に他のメンバーが保存した更新を、上書きすることがある

**起きる条件**

同期はまず一覧を作り、その一覧をもとに何をアップロードするかを決めます。アップロードの直前に Drive 側をもう一度確かめてはいません。そのため、次の順で起きると競合として検出されません。

1. 自分の同期がリモートの一覧を作る。この時点で A は v1。
2. 他のメンバーが A を v2 にしてアップロードする。
3. 自分の同期は「A はローカルだけが変わった」と判断し、v3 で上書きする。

**起きること**

v2 は競合コピーを作られずに Drive 上で v3 に置き換わります。他のメンバーの Obsidian では、次の同期で A が v3 にダウンロードされ、v2 の内容はローカルからも消えます。

**頻度**

次の二つが重なったときだけ起きます。

- 二人が**同じファイル**を、前回の同期以降に編集している。
- 二人の同期が**ほぼ同時に**走る。目安は、一方の同期の実行時間（数秒〜数十秒）の中に、もう一方のアップロードが入ること。

編集すると 3 秒後に同期が走るので、実際には「二人が同じノートを数十秒以内の差で保存した」ときに起こりえます。このプラグインは、同じノートを複数人が同時に編集する使い方を想定していません（[README](../README.md#向いていない用途)）。担当や時間帯でノートが分かれている通常の使い方では、まれにしか起きません。

**復旧のしかた**

Drive はファイルの過去の版を保存しています。Google Drive の Web 画面で A を右クリックし、「ファイル情報」→「版を管理」から v2 をダウンロードできます。Google の既定では、版は 30 日間または 100 版まで保存されます。

**避けるには**

同じノートを同時に編集しないでください。どうしても必要なら、編集する人を一人に決めてください。

**今後の対策**

アップロードの直前に Drive 側の `md5Checksum` を取り直し、一覧を作った時点と違えば競合として扱う方式を検討しています。追加の通信はアップロードするファイル 1 件につき小さな問い合わせ 1 回です。この方式でも、取り直しからアップロードまでの間に、ごく短い隙間は残ります。
